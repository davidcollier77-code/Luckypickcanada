# LuckyPickCanada — CodeRabbit CLI Review Instructions

These instructions are supplied explicitly to local CLI reviews by
`scripts/coderabbit-cli-review.sh`. They are intentionally separate from
`AGENTS.md` and the CodeRabbit GitHub App configuration.

## Review goals

- Act as an independent, read-only second opinion. Report findings; do not
  edit files, commit changes, open pull requests, or make repository changes.
- Prioritize reproducible correctness bugs, security weaknesses, data-integrity
  risks, regressions, broken failure handling, and material performance issues.
- Prefer high-confidence, actionable findings over stylistic preferences,
  speculative concerns, or minor nits.
- State the affected file/location, conditions needed to trigger the issue,
  likely impact, and a practical fix.
- Separate verified observations from assumptions. Never claim a test, build,
  command, or runtime behavior was verified unless evidence actually supports it.
- Check whether the concern is introduced by the reviewed diff before reporting
  it as a regression. Avoid duplicate findings and findings already handled by
  the change.

## Project-specific review focus

### Application and API code

For `app/**`, `components/**`, and `functions/**`, prioritize behavior
regressions, safe input handling, error states, accessibility, responsive
behavior, and compatibility with the existing Next.js/React application.
Do not recommend unrelated redesigns or wording changes.

For `app/api/**`, inspect server-side validation and authorization boundaries,
rate limits, duplicate protection, safe error handling, database writes, and
external-service trust boundaries. Do not trust client-provided state when the
server can validate it.

### Security and dependency handling

For `.github/workflows/**` and `.github/scripts/**`, inspect least-privilege
permissions, pull-request/fork trust boundaries, secret exposure, event
conditions, fail-open/fail-closed behavior, and whether a failed security scan
or test can be silently ignored. Preserve raw security evidence; do not suggest
broad suppressions or scan-path exclusions to hide findings.

For dependency manifests and lockfiles, focus on vulnerable or unexpectedly
changed versions, integrity and reproducibility, and whether manifest/lockfile
changes agree. Avoid suggesting dependency updates without a concrete reason.

### Tests and infrastructure

For `tests/**`, `__tests__/**`, and other test files, look for missing
negative controls, untested error paths, brittle timing assumptions, weak
assertions, and regressions in existing behavior.

For `workers/**`, inspect Cloudflare Worker request trust boundaries, safe
secret handling, error paths, and runtime compatibility. Do not treat a review
as authorization to deploy or change production settings.

### Scope and reporting

- Preserve the existing LuckyPickCanada experience, its approved behavior,
  and unrelated working systems.
- Do not recommend changing `AGENTS.md`, repository governance, GitHub App
  settings, CI workflows, deployment configuration, secrets, or production
  environment values unless the reviewed change clearly requires it.
- Explain trade-offs when a recommendation could change user-visible behavior.
- A clean review means no actionable issue was found in the reviewed scope; it
  does not prove the entire repository is defect-free.
